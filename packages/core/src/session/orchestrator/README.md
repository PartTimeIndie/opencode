`orchestrator/{view,controls}.ts`, `packages/server` and the verified pluginhost
`sessionOrchestrator` endpoint. `api.host.sessions.orchestrator` is a scoped client,
not a child-execution grant. Its writes are serialized per Session; disposal and
server changes reject stale responses and queued work. Plugin identity, capability,

current configuration is refreshed at commissioning, provisioning, admission,
provider and child-write gates, including for mirror children. Missing runtime
wiring is disabled. Tool execution checks admission before and after awaited
before-hooks. Refusals remain typed `Blocked` errors, not internal defects.
Status, pause/draining and conservative retirement do not require re-enabling
execution. A Main may hold at most four worker slots and must respect held task
resources itself.

## Responsibilities and boundaries

- The planning store owns revision-checked Main settings, proposals, dependency ordering, planning slots and resource reservations. An inbox row shaped as `user`, a parent ID, a proposal, or a reservation is **not execution authorization**.
- The checkout resolver supplies a physical Git checkout root shared by root/subdirectory Sessions, but not by independent clones or worktrees. Non-Git directories keep their physical directory identity. The store pins this identity and refuses later placement drift during configuration, planning and reservation. Filesystem resolution runs outside the write transaction; the transaction then rechecks Session placement. Moving a checkout requires a future explicit reconciliation procedure, never automatic re-anchoring. The commissioning tool resolves all proposed `path:` resources through `LocationMutation` before planning any task, then rejects paths outside the active Location rather than implying external-file approval. A later task with invalid resources, a duplicate ID or a non-earlier dependency cannot provision an earlier sibling; a real junction alias shares the same reservation identity. After asynchronous path resolution and before each plan/reservation, the tool rechecks the private Main owner and its live lease. String normalization alone cannot resolve symlink aliases of prospective file targets. These planning keys do not yet enforce actual file or Shell writes; that integration remains a hard release gate. Root and UNC keys remain distinct and normalized keys round-trip. macOS case folding is conservative and may over-block on case-sensitive volumes; only Windows was exercised here.
- Claimed tasks remain ownership evidence even if additive startup repair recreated an empty reservation table. An unknown repaired checkout identity blocks admission rather than freeing capacity. Missing non-defaulted required columns are not safely auto-repairable. This is not general corruption recovery: losing/recreating the task table or manually editing resource identities destroys ownership evidence and requires verified backup/reconciliation, not continued admission based on apparently empty tables.
- The mirror workspace adapter is in `orchestrator/agent-mirror.ts` in Core. It creates independent Git repositories and private working files, requests filesystem COW where supported, and safely uses copies otherwise. Git uses `/dev/null`, not Node's Windows device name. Borrowed Git objects are dissociated. No network sync, worktree creation, writable-hardlink fallback or physical-space saving is implied.
- Mirror manifests distinguish existing files, inherited tracked deletions and requested untracked files that were excluded (ignored or absent), respecting user/system ignore policy. Git filenames require valid UTF-8; sparse checkouts, tracked symlinks/submodules and unsupported portable paths are refused. Destination file modes are set and verified. Mirror-local `core.autocrlf=false` keeps child Git consistent with the byte basis; other Main repository-local settings are not inherited. Failures retain task-owned diagnostic directories. A future cleanup owner must verify `owner.json` and current contents; directory names alone are not ownership proof. Mirrors are not OS sandboxes.
- `session/fork.ts` captures a read-only, transactional provider-turn boundary at the exact current event sequence, with its context epoch, source history and observed model/agent. It refuses stale fences, pending/held inputs, incompatible epochs and unfinished tool pairs. The sole exception is Main's trailing unfinished assistant with exactly one running `orchestrator` tool part; `finish` is still absent while that tool executes and is written only after settlement. A bound commission excludes that call together with its exact promoted assignment user, then captures the preceding completed provider turn (or an empty completed basis on the first turn). The current call supplies the actual agent/model even if the previous turn used another model. A premature `finish: "tool-calls"`, an unbound trailing assignment, or empty/mixed call parts cannot pass this exclusion. This exception does not create a child, remap IDs, clone attachment ownership or attest authorization. Source entries are not clone-ready. Main may still own an activity between turns; this capture does not claim activity/background-job settlement. A future host snapshot operation must revalidate the event fence after filesystem capture and before provisioning. `AgentMirror` only records the caller's `throughSeq` label; its manifest is not proof of that recheck.
- `session/fork-import.ts` prepares a database-bound opaque token outside the write transaction, checks attachment bytes against their content hashes, and materializes into a fresh parented child after recapturing the exact source fence/history/policy. It assigns new message and attachment IDs, remaps synthetic Session references and attachment URIs, and drops message metadata, assistant snapshots, source accounting and custom controls. Imported cost/tokens/generation measurements cannot be refunded from the child's totals during revert cleanup; source rows remain unchanged. The import projector rejects such fields and unfinished assistant/tool/shell history even during direct event replay. Historical tool call IDs remain paired dialogue, not executable grants. It imports no inbox, activity, question or delivered file-knowledge rows. This is not yet child creation, inherited execution policy or host admission.
- Fork message/epoch/attachment events replay independently. Checkpoint adapter v5 retains event-backed `att_fork_` references and validates their ownership; that namespace is not authorization. Cleanup detaches removed message parents to Session-level attachment ownership without changing ordinary/foreign attachments. Compatible normalized v4 checkpoints are hydrated before upgrade or mutation. Legacy absent generation counters take the existing SQLite zero default; recorded counters are retained.
- `EventV2.atomic` defers sync/UI/wakeup notices until the outer commit. Nested atomic calls use savepoints and separate notification queues. Publication is sequential and bound to the transaction's owning fiber: inherited concurrent publishers and raw nested savepoints are rejected before guards or writes. Scopes expire at settlement. Explicit cancellation after commit may stop remaining advisory observer delivery without undoing durable rows; callers reconcile through durable events, not a second blind write. Cancellation of the transaction body rolls back promptly; the adapter restores the caller's interruptibility for the timeout supervisor while preserving masked cleanup writes and timeout protection.
- `session/mirror.ts` prepares **content-only** B→K changes against current M and refuses partial patches on conflicts. Applying a returned patch still requires host permissions, reservations, the Session mutation journal and `FileMutation.transact`. Full integration must additionally preserve and guard file modes, including executable bits; a caller must refuse missing or differing mode evidence rather than silently applying a content-only patch. The current content seam is not a complete merge service.

## Commission and shared provisioning

**Delegated questions.** A managed child's blocking question is durably delegated to its Main session: the child keeps its own blocking row (waiting, exact tool-retry binding and orphan semantics unchanged) while an active mirror appears under Main with `delegatedFrom` provenance. The mirror never occupies Main's exclusive active question slot and never binds the child's tool-retry key. The pair settles together exactly once — a reply or dismissal on the mirror resolves the child's row with a durable receipt, and a child-side answer, rejection or activity-end orphan closes the mirror. Ordinary sessions are unchanged.

- `commission.ts` obtains fresh single-use Permission consent for the exact promoted assignment. Full access and remembered grants do not bypass it. The durable receipt binds the exact trailing running assistant/tool call, actual model/variant, agent, settings and effective policy, while the private live Main owner is required before asking and after the answer. Another tool part, a stale earlier assistant, or a later stored call ID fails before a new consent. Exact retries reconcile; revoked receipts cannot be replaced by a new approval. A versioned assignment-derived family is used by Main from the promoted input's first provider request, persisted only after host approval, and then routed to bound children as a provider cache key and affinity header. Existing valid family IDs remain unchanged on retry; revoked or malformed receipts never produce a replacement family. Neither this routing nor a generic Chat HTTP fixture proves a shared serialized wire prefix or an actual provider cache hit.
- The commission schema has a fail-closed `revoked=true` default. Normal populated upgrades preserve explicit active/revoked values and family IDs; additive repair of a missing revocation column revokes existing rows rather than manufacturing approvals.
- `provision.ts` prepares a database-bound opaque token for shared-checkout **and** mirror tasks, checks the physical checkout and completed source fence, and inherits actual model/variant plus the delegable tool intersection and permission ceilings. It atomically publishes Session creation, imports sanitized history, binds the task and admits its assignment. Shared children keep Main's checkout directory; mirror children are placed in their physical mirror directory and the task records `mirror:<basis-id>`. Main-only metadata and safety approvals are not copied. Source/task/policy/owner drift and competing preparations fail without partial children. Retry of the same committed token only returns the existing receipt. The mirror adapter seam is `orchestrator/mirror.ts`; its production layer roots private copies under the global data directory and delegates to `AgentMirror`, which now lives in Core (`orchestrator/agent-mirror.ts`) with its own test matrix. Mirror creation runs outside write transactions; a failed creation retains the claim and the task-owned diagnostic directory.
- `tool/orchestrator.ts` is a production commissioning caller behind capability `orchestrator`, with no installed manual skill granting it. It obtains the bound host consent, plans and reserves tasks, and provisions ready shared or mirror tasks that win a slot (mirror requires a configured adapter and is refused rather than converted to shared). Provisioned children intentionally remain **`starting` and non-runnable until the guarded admission transition** below. A failed capture/provision after reservation retains the unbound claim and slot, including across crashes. Exact retries report that state rather than replaying preparation or freeing claims. The explicit `pauseUnbound` seam fences a `reserved`/`snapshotting` task of either mode to `paused` under a private live Main owner, expected task revision, valid commission, matching workspace settings, intact reservations and absent child/basis/cache evidence. It invalidates competing prepared tokens but keeps slot and claims; it is not called automatically by tool retry, does not touch mirror directories, does not attest a dead process, and is not a release decision.
- Awaited registry hooks and history imports require subsequent live-owner, lease, agent and effective-policy revalidation before commit. SQLite transactions do not freeze those process-local facts. The replayable `agentPolicy.source.type=orchestrator` identity blocks both activity admission and direct runner entry if local task rows are absent after replay/repair. Ordinary Sessions remain unchanged.

## Lifecycle rules

A terminal task status does not prove that its child stopped writing. Never release slots or reservations merely on `done`, `failed`, `cancelled`, a cache miss, an archive toggle or process expiry.

`releaseUnstarted` only releases paused/terminal tasks with no bound child, including an archived Main's own task. For an unstarted paused proposal, release it, transition to `waiting`, then reserve again. Exact proposal retries reconcile; state mutations require the current task revision, and callers reconcile lost replies by reading stored tasks before another mutation.

`assignChild` and `settleChild` remain **unprovisioned store seams**. `assignChild` binds one existing parented child session to a snapshotting/starting task atomically and idempotently, refuses foreign/missing/Main-role candidates and never frees the slot. Binding is not host attestation, fork provisioning or permission inheritance.

`settleChild` requires the actual `SessionExecution` coordinator's idle exclusion across its immediate database transaction. Missing/noop owners fail closed. It releases only paused/terminal tasks, after every recorded activity is closed, terminal, unowned and without a pending turn-completion continuation; pending inputs, open questions and native mutation uncertainty block release. Zero activities also block. Claims remain through review/integration. A related background job blocks release while its owner cleanup is still unknown: `background_job` now carries a per-reservation `cleanup_token` plus `time_owner_settled`, and only the owning `TaskJob` generation acknowledges cleanup after its entire job scope (including finalizers) closed. Terminal status, lease expiry, remote cancellation and repaired legacy rows all remain deliberately unknown; do not delete job or pending-mutation rows to work around this fence.

`Activity.open` checks durable task admission under its existing transaction. It now also runs the production start transition `OrchestratorCommission.admitChild`: a bound `starting` child moves to `checking_cache` inside that same admission transaction only while its commission is valid, orchestration control is active/draining and the checkout identity still matches; every failure blocks admission and keeps `starting`. The LLM runner additionally requires the matching live owner scope supplied by `SessionExecutionLocal`, checks its activity lease, and rechecks at provider-turn entry. Direct runner calls cannot borrow another drain's durable lease. Rejection occurs before settlement/title hooks, and inherited owner tokens expire at scope exit. This closes tested resume/wake/continuation and direct-runner paths after release; it does not attest arbitrary shell/plugin/external writers. The first-response cache gate is described below.

Physical placement resolution happens before that transaction through `OrchestratorCommission.prepareAdmission`: it resolves Main and child checkouts outside SQLite, pins task id/revision plus both directories into an opaque process-local token, and `admitChild` revalidates token, revision, placement and archive state inside the transaction. A forged/absent token with a managed task, revision drift or placement drift is a typed `OrchestratorExecution.Blocked` failure from `Activity.open`, never a defect or an ordinary session.

**Workspace write/Shell enforcement.** `orchestrator/reservations.ts` turns planning keys into tool-level guards. `write`, `edit` and `apply_patch` revalidate the physical checkout identity of a managed child before every mutation and refuse targets outside the task's reserved resources; shell (`bash`) requires a `project:*` reservation for shared children because command output cannot be bound to single paths. Mirror children write inside their private copy, which remains an isolation copy, not an OS sandbox. A session carrying orchestrator policy without a task row, or a managed child without checkout evidence, fails closed. Ordinary sessions are unaffected.

**Guarded mirror integration.** `orchestrator/integrate.ts` is the owning merge-back seam for mirror tasks: it accepts only a bound mirror task in `integrating` state with its slot, `mirror:<basis-id>` binding, valid commission and revalidated Main checkout identity. The task row additionally stores the host-captured `basis_digest` of the manifest bytes recorded at mirror creation; child-side edits to `.git/opencode-mirror.json` cannot rewrite basis evidence even when its IDs still match. `owner.json` is checked semantically and rehashed within the integration attempt; its arbitrary bytes are not separately persisted as a host-bound digest. The mirror manifest supplies the recorded basis hashes, so the comparison needs no basis bytes: child deltas apply only while Main still matches the recorded basis, child deletions integrate as guarded deletes, Main-side drift under any target refuses the whole patch without partial writes, child mode drift refuses everything, and applied changes go through `FileMutation.transact` with post-write hash verification, verified file modes and Main-owned journal records under the commissioning provenance. Every observed child content/mode pair is rechecked under the final commit fence, so child edits racing the native target locks refuse the patch instead of integrating a stale preparation. Integration also requires active/draining control with matching mode/checkout and settled job cleanup for both Main and child. This seam is not yet wired to a public operation; the host/API surface that triggers integration (and the reviewing-state flow around it) remains open.

Do not introduce a model-controlled `settled: true`, delete/clear a child link to evade these checks, or use `ON DELETE SET NULL` to turn a started child into an apparently unstarted task. Child/input foreign keys retain that evidence. Recursive deletion preflight now refuses configured Mains and referenced children, independently of user-pin overrides. The actual delete-event projector rechecks ownership inside EventV2's immediate transaction, so later configuration/binding cannot slip past an earlier preflight. Checkpoint replacement also refuses to delete/reinsert a managed Session: its projection does not contain orchestration ownership. `SessionOrchestrator.retire` is the explicit retirement protocol: under the live execution owner's idle exclusion and a revision fence it moves a fully settled orchestration (every task terminal, or paused with its slot already released; no claims held) to `control: "retired"` while keeping every commission/task/child row as an admission tombstone. A retired Main refuses new planning, and deletion/archive protection keeps applying. Retirement deletes nothing: mirror directories, job rows and reservations need their own verified cleanup owner. Cold archival independently excludes Mains and referenced children and rechecks eligibility in its deletion transaction. This is conservative preservation, not a general cleanup service.

A cache result of `low` or `unknown` parks that child. With interaction on, Main chooses the approved Main-only or separately authorized ordinary-subagent route; with interaction off, Main continues. Do not add an automatic cache retry/warm-up lane or a blind `blocked_cache -> running` transition. The configured threshold is captured per proposal; the current interaction toggle remains live so changing it affects unresolved decisions.

## First-response cache gate

`orchestrator/cache.ts` is connected to the shared LLM runner, after provider-stream timeout/metrics observation and before publication, tool hooks/execution and file-knowledge delivery. It consumes one durable attempt before subscribing to the HTTP source and buffers its events. Only a clean finish with valid inclusive input/cache-read counts at the task's captured threshold moves the task to `running` and releases the buffered events. Ordinary sessions and accepted follow-ups with unchanged profile and valid accepted evidence use a read-only fast path. Changed/missing profiles or corrupt evidence park durably before follow-up HTTP; they retain claims and cannot retry. Validate stored selection before runner hooks and actual resolved selection before compaction/vision helpers, then recheck at the stream gate. This preflight does not consume a fresh first attempt. A required vision/compaction helper parks both fresh and accepted children before helper HTTP: the helper has a separate profile and cannot borrow a regular response's cache acceptance. Compaction checks this at each actual summary request, including manual compaction and retries; existing saved vision analyses need no provider request. The prepared-request profile now includes a versioned digest of route/defaults/static endpoint, actual SDK adapter/provider/backend ID, instructions and chronological system updates, tools, generation/options/HTTP overlays, late host context, epoch and effective policy. The permission service supplies configured and inherited rules, access-control mode, saved grants and safety-review decisions; tool-materialization rules alone are insufficient. The digest is built after plugin transforms and checked before provider HTTP, then checked again at the stream gate. Only selection plus digest is persisted, never raw headers, bodies or instructions. Growing dialogue and the host's per-input attribution header are excluded. Dynamic endpoint functions, missing permission snapshots and unknown SDK transport identities fail closed. This detects configuration drift, not opaque adapter/auth equivalence or wire-prefix affinity; persisted family provenance remains required.

Low, missing, malformed or failed evidence parks the task without releasing its slot. Raw failures and interrupts retain their cause; provider-error diagnostics can still be published, but withheld tools/text/successful finishes cannot escape rejection. The runner refuses retry and chain lanes for these parked attempts. A crash leaves a consumed unknown marker and cannot trigger a new first request. A pause or changed task revision prevents late acceptance. The first-response buffer is capped at 8 MiB / 16,384 events; crossing the bound parks rather than retries. Hosted/native provider tools, including tool-bearing raw HTTP body overlays, are refused before this first request because local buffering cannot undo remote execution. A consumed attempt is rejected before model resolution/title helpers. Raw provider failures retain their status, retryability and Retry-After; a provider child interruption is distinct from explicit human stop and does not terminalize a sibling owner.

A rejected response's own measured usage is not inherited fork accounting and must not be discarded. The runner records it with an error-only `Step.Ended`, without publishing the buffered text/tools or a successful finish. Attempt settlement and accounting commit in one `EventV2.atomic` transaction, fenced by the durable pending-attempt token. Callback failure rolls back both while leaving the attempt consumed. A concurrent pause can deny acceptance without erasing measured usage or reverting the newer state. Duplicate replay/resume must not charge twice.

The AISDK usage adapter preserves unknown cache reads for OpenAI-compatible Chat/Responses responses whose raw `prompt_tokens_details.cached_tokens` / `input_tokens_details.cached_tokens` is missing or malformed, instead of treating the SDK's synthetic zero as a measured zero. Explicit zero remains measured, including at a zero threshold. Other SDK usage shapes retain their existing mapping; these tests do not certify every provider's accounting semantics.

The planning store's `recordCache` cannot update a bound child or consumed attempt. Its childless planning evidence cannot later become an execution grant: child binding is restricted to snapshotting/starting. Real children use only the runner gate. Do not expose this planning seam as a public usage/acceptance endpoint.

This gate is not a cache-affinity implementation, user authorization or child-provisioning service. The model/profile label is diagnostic; it does not prove shared serialized prefixes. No personal skill or toolbar is installed while the remaining runtime gates are unfinished.

### Late host context boundary

`LLMRequest.runtimeContext` is typed trusted-caller context, separate from chronological `Message.system` updates. The route must explicitly support `late-system`; otherwise a nonempty runtime context is rejected before transport. Native OpenAI Responses appends it after history. The real OpenAI Chat/Responses SDK adapters preserve that order and system rank, including reasoning models whose SDK default would otherwise rewrite system roles. Unsupported SDKs retain their ordinary single-leading-system layout. Request/default raw prompt overrides, provider-side history and removed system messages cannot be combined with runtime context.

The Session runner derives its own identity and actual Location directory after plugin transforms, on every supported request. It does not copy a parent ID as current identity or include host identity in helper requests. Request footprint metrics include runtime context. This establishes tested serialization, not wire-equivalent parent/child prefixes, family affinity, live cache acceptance or host assignment authority. No new execution grants come from this field.
