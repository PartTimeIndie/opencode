# Agent tools and skills across projects

Agent definitions remain visible across projects. Tool visibility, permissions, and skill discovery are separate boundaries:

- Global agent tool entries can use `scope: { mode: "global" }` (default, including future projects) or `scope: { mode: "projects", projects: ["<canonical absolute project path>"] }` (closed whitelist). An empty project list exposes the tool nowhere. A project-local agent may narrow a central policy, never widen a central project restriction. Even explicit wildcard tool entries must not bypass it.
- `projectPermissions` are per-project overrides (`allow`, `ask`, `deny`) and default to `Inherit`. Selecting a project is never a permission grant. Preserve scope, delegation metadata and permission overrides when editing a tool entry or materializing inherited tools. Session delegation retains its inherited allowlist ceiling.
- Global `skill_scopes` is keyed by the original on-disk skill directory. Project-local skills can be shared without copying source files: the selected source is registered in allowed projects and filtered before same-name skill precedence. The most specific matching restriction wins, including when discovered through a symlink alias. URL and embedded skills have no on-disk directory scope in the manager.
- Match Windows project paths case-insensitively after separator and dot-segment normalization; keep POSIX paths case-sensitive. This is a path-matching contract, not a rewrite of durable project IDs.
- Agent UI: Settings → Agents → Tool access → each tool's **Verfügbar in** control. Skill UI: Plugin Manager → Skills → **Verfügbar in**. Save agent edits explicitly. Skill scope changes write global configuration. An already-running model turn retains its old tool list; reload/new sessions may be needed after config changes.
- To diagnose an absent tool, compare tool registration, global `agent.<name>.tools`, project `.opencode/agents/<name>.md`, current session `agentPolicy`, materialized permissions, and `session runner request metrics` `tool_ids`. An explicit project tool list replaces the earlier list; a permission rule cannot resurrect an omitted tool. `/codex-image` is a command, not a tool grant.
- Skill-gated tools remain registered while hidden. Their manual skill must declare `capabilities: [<capability>]`, the host must grant the same capability through `skill_capabilities`, and the current Session/agent lease must be active before advertisement. Agent/project visibility, explicit lists, scope and Deny remain restrictions; reading the skill file is not activation. Do not bypass hidden tools with direct HTTP, shell or database calls.
- Visibility and Ask are independent: `ask` keeps an otherwise eligible tool advertised, but does not activate a missing skill capability. Native `spawn_agent` also requires fresh single-use host consent on every invocation, even under Full Access, remembered Allow or safety review. Pending/rejected consent creates no Session; consent must never be remembered as Always. Verify loader → lease → registry and native handler → actual Permission service separately; test fixtures do not prove the installed app reloaded the change.
- Source changes alone are not installed desktop changes. Verify the full prod desktop deploy status and installed artifact before telling the user the new UI is ready. Never stop/restart OpenCode without explicit current-chat approval.
