# Composer send preparation

The app host owns a volatile, target-pinned Send transaction for recordings that must finish before submission. The app-plugin API is `host.composer.registerSendPreparation(target, preparation)`. The target has the exact project directory, optional Session ID, and composer ID. The preparation supplies a unique `operationID`, `isActive()`, `subscribe(listener)`, and `prepare({ intentID, signal })`. It resolves with `{ ok: true, text }`, `{ ok: true, insertionReceiptID }`, `{ ok: false, error }`, or `{ ok: false, error, insertDraft }`. The host—not the plugin—submits the message.

On human Send/Enter, the host reserves the operation synchronously, captures the original draft, cursor, attachments, pending context, agent, model, variant, chain, delivery choice and target, then asks the plugin to finish. The plugin stops recording, awaits transcription and the improvement settings frozen at Send, and returns the final text. No second preview is required. The microphone Stop button remains insert-only. Processing/improvement errors fail closed: neither Continue nor raw transcript is automatically sent. A preparation registered before Send is not itself approval.

`insertDraft` keeps a blocked dictation instead of dropping it. The send stays blocked; the Speech plugin uses it when its improvement model fails, so the composer shows the raw transcript as an unsent draft with "Improvement failed - raw transcript inserted, not sent". The host inserts `insertDraft` into the live composer itself, after `prepare` settled and before it presents the blocked result, so a plugin-side insertion can never race the send rollback: the blocked presentation only restores the approved prompt while the draft is still unchanged. A cancelled or unknown send discards `insertDraft`; a failed insertion is folded into the blocked error. Submissions without draft support keep the plain `{ ok: false, error }` contract.

The host runs the captured before-submit handlers and final appends against a transaction-local draft. Editor unmount does not revoke an already captured hook lease; plugin unload does. After access-control and worktree readiness, it submits through the normal host request builder with the pinned message identity and ordinary permission/model settings. A queued recording send dispatches immediately like a typed send during a busy session: the server holds the queued message until the running turn finishes, and the composer pending state ends as soon as the transcript is dispatched. A queued approval stays in memory; it is never written to the persisted follow-up queue. The original tab can be inactive during processing. An explicit target-tab close, server change, plugin unload or local cancellation revokes unsent work. Reload/app exit drops approval without replay. Once request dispatch begins, an ambiguous failure is **unknown** and never triggers automatic retry; unchanged command-shaped drafts require an edit before manual resend.

`composer.insertText({ ..., operationID })` can return a host-issued `insertionReceiptID` if manual Stop insertion races with Send. The receipt is bound to the exact target and operation and used once. The host checks the pre/post draft snapshots; it never decides that text was already inserted solely because the phrase appears in the draft. A changed draft blocks dispatch instead of duplicating or overwriting content.

A plain `composer.submitText` call remains a guarded Continue-style insertion into the active empty composer. It is **not** an alternative for prepared Send: navigation checks, permissions, attachments, and normal hooks must not be bypassed. The prepared API adds behavior without changing the normal submit path. See `packages/app/src/plugin/composer-send-intent.ts`, `packages/app/src/components/prompt-input/prepared-submit.ts`, and the Speech plugin's maintained source under `.opencode/plugin-sources/speech-to-text-app/`.
