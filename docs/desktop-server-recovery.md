# Windows tray and local server recovery

## Ownership and entry points

The Windows desktop main process owns the tray and the local utility-process server. `packages/desktop/src/main/index.ts` wires window lifecycle, status delivery and deliberate shutdown. `server.ts` owns the Electron transport; `server-supervisor.ts` owns restart state and timers. The renderer and tray show the same server status and offer retry only after the bounded restart budget is exhausted.

Closing the main window hides it only when a tray was created successfully. Opening from the tray or a second launch restores and focuses the existing window. Explicit Quit, update, relaunch and Windows session end retain real shutdown behavior. No Windows autostart or external watchdog service is installed.

## Restart contract

- Supervise only the desktop-owned local sidecar. Remote and WSL servers are separate.
- Unexpected exits, including exit code zero and pre-ready failures, consume at most five replacement attempts with 1/2/4/8/16-second delays. Five minutes of uninterrupted healthy operation resets the budget.
- Startup and health verification share a 120-second deadline. Each health request is bounded to three seconds. Cancel obsolete timers and polls. Production data has previously needed more than 60 seconds to start under load.
- Confirm old-process exit before starting another generation. If exit cannot be confirmed, show a blocked state rather than allow a manual overlapping start.
- Deliberate stop cancels backoff and startup. Do not restart after Quit or update. Do not kill a running server merely because one health probe failed.
- A sidecar stop waits up to twelve seconds for its observed exit. A deadline does not itself authorize a kill: show a native dialog to retry, cancel, or explicitly force the local utility process to stop, warning that active work and writes can be lost. Force only the owned child and still require an observed exit; if it cannot be confirmed, block parent exit and replacement. Retain the server reference, tray and controls on cancellation or failure, and permit a later deliberate exit check. Propagate listener cleanup defects instead of turning them into a successful `stopped` acknowledgement. WSL sidecars use their separate existing shutdown path and are not covered by this local-sidecar confirmation.
- Reuse the app-lifetime endpoint, ephemeral authentication and existing data/channel paths. Never log credentials. No recovery of the Electron parent itself is promised.
- The parent logs state transitions, each local sidecar generation's PID at spawn, and its PID, exit code and lifetime at exit. The sidecar sends a numeric-only process sample immediately and every 30 seconds: uptime, RSS, V8 heap usage/limit, external memory and cumulative user/system CPU time. The parent validates the exact sample shape before recording it in `utility.log`; session content, paths and credentials are excluded. Correlate the PID and timestamps with Crashpad dumps when investigating a native exit. A sample shows resource pressure but does not identify a crashing native function; the matching dump still needs symbols.
- Electron utility-process fatal errors supply `(type, location, report)`, not an `Error` object. Retain the native location and bounded JavaScript/native stack frames through `sidecar-fatal-error.ts`; never log or save the raw Node diagnostic report, its environment, command line, arbitrary error properties or worker reports. A native V8 fatal error is not proof of a particular plugin failure or memory exhaustion. Match the observed exit to its Crashpad dump and exact runtime symbols before choosing a workaround; a source diagnostic fix is not a deployed crash-prevention fix.

## Session recovery

`session/desktop-recovery.ts` is a process-private capsule configured by the utility entrypoint before server startup. It is not a config flag, environment authorization or HTTP endpoint. The Core execution layer acknowledges its actual generation owner over the private parent port. Only an acknowledged, observed-exited predecessor is passed to later generations. No PID guessing, foreign-process takeover or model-supplied authority is involved.

`SessionExecutionLocal` schedules a distinct recovery demand through the same process-local coordinator. It cannot join or queue behind other work, a host idle transaction, or a human stop. The normal startup delay and lease fences remain in effect. Unknown owners retain ordinary stale-activity interruption without replay.

The existing activity row is the durable admission receipt: an immediate transaction checks the expected activity and predecessor owner, checks `CrashGuard`, then atomically changes owner and increments the recovery count. A duplicate admission cannot match the old owner again. Crash recovery is capped at three claims per activity. A subsequent crash may recover a claimed activity only with proof for that new owner. No schema migration or separate queue of synthetic user prompts is needed.

The guard is intentionally conservative. It pauses for missing/changed saved model or agent, child ownership, archived/reverted sessions, pending questions (including orphaned questions), unknown tool/shell outcomes, pending native file mutations, independently managed background jobs, newer/unprocessed inputs, insufficient event evidence, prior provider retry/failure, or exhausted recovery attempts. It does not clear locks, uncertainty, question answers or scheduler receipts. Prior provider retries pause rather than acquire a fresh retry budget. Recorded model/agent switches also pause, even if the saved selection was later changed back. Other safe sessions can proceed.

The runner starts a fresh turn from stored history with the same session and selections. Completed tool results are reused, not re-executed. Unpersisted tokens, provider streams and ephemeral provider caches are not recoverable promises.

## Deliberate full-app restart

A graceful full-app shutdown uses a separate existing path: closing the execution scope releases its owned running activities with the durable `owner-shutdown` reason. Startup recovery may continue only that bounded controlled-shutdown cohort. It does not require or invent a private crash predecessor. User-stopped and unknown crashed activities are not part of that cohort; pending blocking questions remain paused until their durable reply or dismissal. A force-killed app is not a graceful handoff.

`session-desktop-drain.test.ts` exercises two successive isolated OS processes sharing a fixture database: the first shuts down real LocalExecution scopes with two live loopback provider streams; the second starts without predecessor authority and completes both saved sessions without repeating completed tools. The separate Surface and stale-owner tests cover paused questions and non-replay boundaries. This does not prove that a particular installed package gracefully releases its sessions, nor that a forced deployment can continue every session. Before deployment, verify the installed shutdown path and current active cohort; do not substitute expired leases, a renderer status response or a new synthetic prompt for a successful handoff.

For an authorized deployment, coordinate a brief maintenance pause with the currently active known agents rather than waiting indefinitely for a naturally empty app. Ask them through `session_send` to finish in-flight tools/writes, save their next step and end their turn safely without starting new work. A delivered message is not proof that they paused: recheck real Activities and background writers, then verify graceful handoff. Do not force-cancel work, read other histories, rewrite receipts/claims or manufacture a resume prompt. After verified deployment, notify the cooperating agents that they can continue their existing authorized work. Coordination does not replace the required user approval to stop/restart the installed app.

Check any inherited external-release input before closing the app. A previously applied descriptor may still expect the pre-installation baseline. Do not renew that baseline or replay the external release to make deployment pass. When the descriptor's declared artifact, its current source and its installed target are all verified byte-identical, a task-scoped deployment can omit that already-applied input while retaining the descriptor and installed package unchanged. Any difference or missing evidence remains a blocker; ordinary release guards still apply to new external changes.

Recovery notices remain durable **system** messages marked `metadata.systemNotice = "server-recovery"`. They are not replacement context baselines and survive epoch rebuilding until normal compaction. The timeline displays them as clearly labeled system notices, not new user turns. Live and reloaded projections must agree and retain the original user parent. Notice text grants no permission. Activity admission/blockade commits before notice publication: another process crash in that narrow gap can leave the durable activity reason without a timeline notice. A successful recovery never starts its provider turn before notice publication; a blocked activity remains blocked even if its notice is missing.

## Verification

Runtime upgrades must respect the package release-age guard. Keep sandboxed preload isolation, PNG-only clipboard attachments, asynchronous clipboard error propagation and invocation revalidation after awaited reads. Decline browser login challenges without an owning WebContents; a utility-process challenge must not inherit another session's credentials. Do not change JIT/performance flags or weaken tests as an unproven native-crash workaround.

- `packages/desktop`: `bun test src/main/tray-lifecycle.test.ts src/main/server-supervisor.test.ts src/main/sidecar-stop.test.ts src/main/shutdown.test.ts src/main/sidecar-fatal-error.test.ts src/main/clipboard-image.test.ts src/main/browser-sidecar-auth.test.ts`; `bun scripts/verify-server-recovery.ts`; `bun scripts/verify-electron-runtime.ts`; `bun run test`; `bun typecheck`.
- `packages/opencode`: `bun test test/server/listener-stop.test.ts test/server/httpapi-listen.test.ts`; `bun typecheck`. Existing platform-specific PTY skips remain explicit.
- `packages/core`: `bun test test/session-desktop-recovery.test.ts test/session-desktop-drain.test.ts test/session-crash-coordinator.test.ts test/session-recovery.test.ts test/session-run-coordinator.test.ts`; relevant history/projector tests; `bun typecheck`.
- `packages/app`: recovery-notice, session-message-adapter and session-live-projection tests; `bun typecheck`.

The Electron recovery fixture uses temporary user data and a real utility-process crash/HTTP restart. The runtime fixture verifies the selected dependency version, real native PNG/JPEG conversion, sandboxed production preload and native watcher events without accessing the OS clipboard. The separate Core fixture exercises real LocalExecution and a loopback model protocol, checking persisted history, selection and completed tool results. These fixtures do not touch installed OpenCode processes, real credentials or real sessions. These source-level tests do not prove that the installed application contains the change. Full prod deployment and installed-app restart require separate current user approval.
